# 第五阶段学习总览：AI 插件 / IDE / Tooling

## 文档目标

第五阶段的核心目标是理解：

> 如何把 AI 能力嵌入浏览器、编辑器和开发工具，让 AI 变成用户工作流的一部分。

前四个阶段你已经学过：

- Stage 1：LLM 基础，让 AI 能对话
- Stage 2：Tool Calling，让 AI 能调用工具
- Stage 3：RAG，让 AI 能查资料
- Stage 4：Agent / Workflow，让 AI 能完成多步骤任务

第五阶段开始进入 **AI Tooling**。这一阶段不只是“调模型接口”，而是要学习如何把模型能力放进真实工具里：

- 浏览网页时总结、翻译、解释高亮内容
- 写代码时解释、重构、生成、局部修改代码
- 在 IDE 侧边栏和编辑器里和 AI 交互
- 通过 AST / Parser 理解代码结构

## 一张图理解 AI Tooling

```text
用户所在工具
  浏览器 / IDE / 编辑器
      ↓
插件层
  读取页面、读取代码、监听用户操作
      ↓
上下文组装层
  页面文本 / 选区 / 文件内容 / AST / 历史记录
      ↓
AI 能力层
  总结 / 翻译 / 解释 / 重构 / 生成 / Inline Edit
      ↓
结果回写层
  插入页面侧边栏 / 替换代码 / 展示 Diff / 生成文件
```

AI Tooling 的关键不是“问模型一个问题”，而是：

> 准确获取用户当前上下文，并把 AI 结果安全地写回用户正在使用的工具。

## 需要建立的核心认知

### 1. AI Tooling 的核心是上下文

网页助手需要知道：

- 当前页面标题
- 当前页面正文
- 用户选中的文本
- 当前 URL
- 用户想执行总结、翻译还是问答

AI IDE 需要知道：

- 当前文件内容
- 用户选中的代码
- 光标位置
- 项目结构
- 相关依赖和类型信息

没有上下文，AI 只能泛泛回答。有了上下文，AI 才能像“工具的一部分”一样工作。

---

### 2. 插件不是普通网页应用

Chrome Extension 和 VSCode Extension 都有自己的运行环境和权限模型。

普通网页应用通常是：

```text
浏览器页面 → 调后端接口 → 展示结果
```

插件应用通常是：

```text
宿主环境
  Chrome / VSCode
      ↓
插件运行时
  Background / Extension Host
      ↓
用户界面
  Popup / Sidebar / Webview
      ↓
宿主 API
  tabs / storage / commands / workspace / editor
```

所以你必须理解：

- 插件代码运行在哪里
- 哪一层能访问页面
- 哪一层能访问网络
- 哪一层能读写编辑器
- 不同层之间如何通信

---

### 3. AI IDE 的难点是“改代码”

解释代码比较简单：

```text
读取选区 → 发给模型 → 展示解释
```

真正难的是修改代码：

```text
读取选区
  ↓
理解周围上下文
  ↓
让模型生成修改结果
  ↓
计算 Diff
  ↓
让用户确认
  ↓
安全写回编辑器
```

工程上不能让模型随意覆盖文件。更好的方式是：

- 限定修改范围
- 生成结构化补丁
- 展示 Diff
- 用户确认后再写入

---

### 4. Parser 让 AI 更懂代码结构

如果只把代码当字符串处理，会遇到很多问题：

- 不知道函数从哪里开始到哪里结束
- 不知道变量属于哪个作用域
- 不知道 import 和调用关系
- 很难做精确重构

Parser 可以把代码变成 AST：

```text
代码字符串
  ↓
Parser
  ↓
AST 语法树
  ↓
函数、变量、类、调用关系
```

AST 不会替代 LLM，但它能给 LLM 提供更准确的结构化上下文。
