# 01 - AI Tooling 与 AI IDE 基础

## 文档目标

这份文档讲清楚第五阶段的总入口：

> AI Tooling 到底是什么，AI IDE 为什么和普通聊天机器人不一样。

学完后，你应该能理解：

- AI Tooling 的产品形态
- AI 插件和 AI IDE 的核心架构
- 上下文、动作、回写三个关键环节
- 为什么 AI IDE 的重点不是聊天，而是“理解并修改工作区”

---

## 1. AI Tooling 是什么

AI Tooling 指的是把 AI 能力嵌入具体工具中，让 AI 直接参与用户当前工作流。

常见形态包括：

```text
浏览器插件
  - 网页总结
  - 翻译
  - 选中文本解释
  - 页面问答

IDE 插件
  - 解释代码
  - 生成代码
  - 重构代码
  - 修复错误

独立 AI 编辑器
  - 类 Cursor / Windsurf
  - 内置代码编辑器
  - 内置 AI 侧边栏
  - 支持 Inline Edit
```

它和普通 AI 聊天产品最大的区别是：

> 普通聊天产品让用户把问题发给 AI；AI Tooling 会主动读取用户所在工具里的上下文，并把结果回写到工具中。

---

## 2. AI Tooling 的三段式架构

所有 AI Tooling 产品都可以拆成三段：

```text
上下文获取
  读取网页、选区、代码、文件、项目结构
      ↓
AI 处理
  总结、翻译、解释、重构、生成、修复
      ↓
结果回写
  展示答案、插入内容、替换选区、生成 Diff
```

### 上下文获取

上下文决定 AI 能不能回答得具体。

例如网页助手：

```text
当前 URL
页面标题
正文文本
用户选中文本
页面语言
```

例如 AI IDE：

```text
当前文件
选中代码
光标位置
周围函数
项目目录
依赖信息
错误日志
```

### AI 处理

AI 处理不是简单地把上下文塞进 Prompt。工程上通常要先做：

- 清洗无用文本
- 控制 Token 长度
- 判断任务类型
- 选择不同 Prompt 模板
- 要求结构化输出

### 结果回写

AI 结果必须进入用户工作流：

- 网页助手可以显示在侧边栏
- 翻译可以展示浮层
- 代码解释可以显示在面板
- 重构结果应该展示 Diff
- Inline Edit 应该只替换用户选中的区域

## 3. AI IDE 的核心能力

AI IDE 不是“多了一个聊天框的编辑器”。它至少需要四类能力。

### 1. 代码上下文管理

```text
当前文件内容
当前选区
当前函数
相关文件
项目结构
终端错误
Git Diff
```

AI IDE 必须知道用户正在改什么，而不是每次都让用户复制粘贴。

### 2. 代码理解

代码理解可以分两层：

```text
文本层：
  把代码当字符串，交给 LLM 解释

结构层：
  用 AST / Parser 提取函数、类、变量、依赖关系
```

真实 IDE 往往会结合两者：LLM 负责语义理解，Parser 负责结构定位。

### 3. 代码生成与修改

AI IDE 的生成能力包括：

- 新建文件
- 补全函数
- 生成测试
- 修复错误
- 重构已有代码
- 局部替换选区

其中最重要的是“修改边界”。

```text
好设计：
  只修改用户选区或明确指定的函数

坏设计：
  模型返回整份文件，然后直接覆盖
```

### 4. 用户确认机制

AI 修改代码前最好让用户看见：

- 修改了哪里
- 删除了什么
- 新增了什么
- 是否影响其他文件

所以 Diff 视图是 AI IDE 的关键组件。

---

## 4. AI Tooling 的典型模块

```text
UI 层
  Sidebar / Popup / Webview / Editor Panel

上下文层
  Page Extractor / File Reader / Selection Manager / AST Analyzer

Prompt 层
  Prompt Template / System Instruction / Structured Output Schema

模型层
  LLM API / Streaming / Tool Calling

执行层
  Replace Selection / Apply Patch / Insert Text / Create File

安全层
  Permission / User Confirm / Scope Limit / Error Recovery
```

你做第五阶段项目时，不需要一开始就把这些全部做完，但必须知道每个模块为什么存在。

---

## 5. 普通聊天应用和 AI IDE 的区别

| 维度 | 普通聊天应用 | AI IDE / AI Tooling |
|------|--------------|---------------------|
| 输入 | 用户手动输入问题 | 自动读取上下文 + 用户指令 |
| 输出 | 一段文本回答 | 文本、Diff、文件修改、页面浮层 |
| 上下文 | 对话历史 | 文件、页面、选区、项目结构 |
| 风险 | 回答错 | 可能改坏代码或误导用户 |
| 核心难点 | 对话体验 | 上下文管理、修改边界、结果回写 |

## 6. 一个 Explain Code 的完整流程

```text
用户选中一段代码
  ↓
插件读取当前选区
  ↓
读取文件名、语言、周围函数
  ↓
组装 Prompt
  ↓
调用 LLM
  ↓
流式返回解释
  ↓
显示在侧边栏
```

Prompt 示例：

````text
你是一个代码讲解助手。

文件名：src/auth/login.ts
语言：TypeScript
用户选中的代码：
```ts
async function login() { ... }
```

请用中文解释：
1. 这段代码做了什么
2. 关键逻辑是什么
3. 有哪些潜在风险
````

注意：这里的 Prompt 不是孤立问题，而是带上了文件、语言、选区等上下文。

---

## 7. 一个 Inline Edit 的完整流程

```text
用户选中代码
  ↓
输入修改要求
  ↓
读取选区 + 周围上下文
  ↓
让模型只返回修改后的选区
  ↓
校验结果
  ↓
生成 Diff
  ↓
用户确认
  ↓
替换选区
```

关键原则：

> Inline Edit 不应该让模型随意改整份文件，而应该让模型只处理明确边界内的代码。

---

## 8. 工程注意事项

### 控制上下文大小

不要把整个项目都塞给模型。优先级通常是：

```text
用户选区 > 当前函数 > 当前文件摘要 > 相关文件摘要 > 项目结构
```

### 控制修改范围

对模型说清楚：

```text
只返回修改后的选中代码。
不要返回解释。
不要修改选区之外的代码。
保持原有函数签名不变。
```

### 做好失败处理

AI Tooling 常见失败包括：

- 页面正文提取失败
- 选区为空
- 模型返回格式不对
- 修改结果无法应用
- 网络请求失败
- 权限不足

这些都要给用户明确提示。

---

## 本节小结

AI Tooling 的本质是：

> 读取上下文，调用 AI，安全回写结果。

AI IDE 的本质是：

> 让 AI 理解用户当前代码，并在明确边界内辅助修改代码。

接下来可以先学习 Chrome Extension，因为网页助手插件是最容易落地的 AI Tooling 项目。
